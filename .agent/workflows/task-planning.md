# 任務規劃工作流程

此工作流程幫助Feature Owner將PRD（產品需求文檔）拆分為結構化、可追蹤的任務列表。

## 前置條件

- ✅ PRD已撰寫完成並獲得批准
- ✅ 架構設計已經確定（至少是高層設計）
- ✅ 技術棧和工具已選定

## 工作流程步驟

### 步驟 1：分析PRD並識別主要功能模塊

閱讀PRD並識別主要功能塊：

1. 列出所有功能需求
2. 根據功能相關性進行分組
3. 識別功能之間的依賴關係
4. 確定優先級（P0 = 必須有, P1 = 應該有, P2 = 可以有）

**輸出**：功能模塊清單

### 步驟 2：為每個功能模塊拆分技術任務

對於每個功能模塊，考慮以下技術層面：

#### 前端任務
- UI組件開發
- 頁面/視圖實現
- 用戶交互邏輯
- 表單驗證
- 狀態管理
- 響應式設計適配

#### 後端任務
- API端點設計與實現
- 業務邏輯實現
- 數據模型設計
- 數據庫遷移腳本
- 服務集成
- 錯誤處理

#### 基礎設施任務
- 數據庫變更
- 緩存策略
- 消息隊列配置
- 環境配置
- 部署腳本

#### 測試任務
- 單元測試
- 集成測試
- E2E測試
- 性能測試
- 安全性測試

#### 文檔任務
- API文檔
- 用戶指南
- 開發者文檔
- 部署文檔

### 步驟 3：使用自動化工具生成任務列表

// turbo
```bash
python scripts/feature-owner/generate_tasks.py \
  --prd "docs/features/[feature-name]/PRD.md" \
  --output "docs/features/[feature-name]/TASKS.md"
```

工具會自動：
- 解析PRD內容
- 識別功能需求
- 生成推薦的任務列表
- 建議任務依賴關係
- 估算相對複雜度

### 步驟 4：細化和調整任務列表

審查自動生成的任務列表並進行調整：

#### 任務描述規範

每個任務應包含：

```markdown
## [任務ID] 任務標題

**優先級**：P0/P1/P2
**負責人**：待分配
**預估工時**：X天
**依賴**：任務ID列表

### 描述
簡潔描述任務要完成什麼

### 驗收標準
- [ ] 標準1
- [ ] 標準2
- [ ] 標準3

### 技術考量
- 相關技術棧
- 需要注意的技術難點
- 參考資料鏈接
```

#### 檢查清單

- ✅ 每個任務都有清晰的描述
- ✅ 驗收標準具體可測試
- ✅ 工時估算合理（1-3天為佳）
- ✅ 依賴關係明確標註
- ✅ 優先級正確設定
- ✅ 任務之間沒有重疊

### 步驟 5：組織任務為Sprint/里程碑

將任務分組到不同的Sprint或里程碑：

#### 里程碑建議結構

**M0: 架構與設計**
- 技術方案設計
- 數據模型設計
- API設計
- 架構審查

**M1: 基礎設施與核心功能**
- 數據庫表創建
- 基礎API實現
- 核心業務邏輯
- 基本前端頁面

**M2: 完整功能實現**
- 所有功能API完成
- 完整前端實現
- 功能集成測試

**M3: 優化與完善**
- 性能優化
- 錯誤處理完善
- 用戶體驗優化
- 安全性加固

**M4: 測試與發布準備**
- 完整測試覆蓋
- 文檔完成
- 部署腳本準備
- 發布驗證

### 步驟 6：分配任務責任人

根據團隊成員的專長和工作負載分配任務：

1. 識別團隊成員技能矩陣
2. 評估每個人的當前工作量
3. 考慮任務的學習機會
4. 確保關鍵路徑任務有經驗的人負責
5. 與團隊成員確認承諾

### 步驟 7：創建任務看板

將任務導入到專案管理工具（如Jira, GitHub Projects等）：

1. 創建Epic對應主要功能模塊
2. 創建Story對應具體任務
3. 設置任務狀態流：待辦 → 進行中 → 審查中 → 已完成
4. 配置看板視圖
5. 設置自動化規則（如自動分配、狀態轉換等）

### 步驟 8：團隊評審會議

召集團隊進行任務規劃評審：

**會議議程**：
1. 介紹PRD和功能目標（10分鐘）
2. 逐個評審任務（30-45分鐘）
   - 任務是否清晰
   - 驗收標準是否合理
   - 工時估算是否準確
   - 依賴關係是否正確
3. 討論風險和挑戰（10分鐘）
4. 確認里程碑和時間線（5分鐘）

**會議輸出**：
- 團隊認可的任務列表
- 調整後的工時估算
- 識別的風險清單
- 明確的承諾

## 任務拆分最佳實踐

### 垂直切分 vs 水平切分

**✅ 推薦：垂直切分**
```
任務1: 用戶登入功能（前端 + 後端 + 測試）
任務2: 用戶註冊功能（前端 + 後端 + 測試）
```

**❌ 避免：純水平切分**
```
任務1: 所有前端頁面
任務2: 所有後端API
任務3: 所有測試
```

垂直切分的優勢：
- 每個任務都能產出可演示的功能
- 早期獲得反饋
- 降低集成風險
- 更好的並行開發

### SMART原則

確保每個任務符合SMART原則：

- **S**pecific（具體）：明確說明要做什麼
- **M**easurable（可衡量）：有清晰的驗收標準
- **A**chievable（可實現）：在資源約束下可完成
- **R**elevant（相關）：與功能目標直接相關
- **T**ime-bound（有時限）：有明確的完成時間

### 任務粒度指南

| 粒度 | 工時 | 適用場景 |
|------|------|----------|
| 太小 | < 4小時 | 避免過度拆分，增加管理成本 |
| **理想** | **1-3天** | **大多數開發任務** |
| 可接受 | 3-5天 | 複雜功能，但需要子任務分解 |
| 太大 | > 5天 | 必須進一步拆分 |

## 常見任務模板

### API開發任務模板

```markdown
## 實現 [資源名稱] API

**優先級**：P0
**預估工時**：2天

### 描述
實現 [資源名稱] 的CRUD API端點

### API端點
- POST /api/[resource] - 創建
- GET /api/[resource]/:id - 獲取單個
- GET /api/[resource] - 列表查詢
- PUT /api/[resource]/:id - 更新
- DELETE /api/[resource]/:id - 刪除

### 驗收標準
- [ ] API符合RESTful設計規範
- [ ] 實現請求參數驗證
- [ ] 實現錯誤處理和適當的HTTP狀態碼
- [ ] 單元測試覆蓋率 ≥ 80%
- [ ] API文檔已更新（Swagger/OpenAPI）
- [ ] 集成測試通過
```

### 前端組件任務模板

```markdown
## 開發 [組件名稱] 組件

**優先級**：P1
**預估工時**：1.5天

### 描述
開發可重用的 [組件名稱] UI組件

### 功能要求
- 支持的props: [列出]
- 支持的events: [列出]
- 響應式行為: [描述]

### 驗收標準
- [ ] 組件符合設計稿
- [ ] 支持所有必需的props和events
- [ ] 響應式設計在移動端和桌面端都正常
- [ ] 單元測試覆蓋主要功能路徑
- [ ] Storybook story已添加
- [ ] 組件文檔已完成
```

### 數據庫遷移任務模板

```markdown
## 數據庫遷移：[描述變更]

**優先級**：P0
**預估工時**：0.5天

### 描述
創建數據庫遷移以支持 [功能名稱]

### 變更內容
- 新增表: [列出]
- 修改表: [列出]
- 新增索引: [列出]

### 驗收標準
- [ ] 遷移腳本可以成功執行 (up)
- [ ] 回滾腳本正常工作 (down)
- [ ] 在開發環境驗證成功
- [ ] 性能測試：索引有效提升查詢速度
- [ ] 數據模型文檔已更新
```

## 檢查清單

任務規劃完成後，確認：

- ✅ 所有PRD需求都有對應任務
- ✅ 每個任務都有清晰的驗收標準
- ✅ 任務依賴關係已標註
- ✅ 工時估算已與團隊確認
- ✅ 任務已分配到里程碑
- ✅ 關鍵路徑任務已識別
- ✅ 風險和挑戰已記錄
- ✅ 團隊已評審並認可任務列表

## 下一步

任務規劃完成後：

1. 開始執行開發工作
2. 使用 [milestone-tracking](./milestone-tracking.md) 工作流程追蹤進度
3. 定期更新任務狀態
4. 在每個里程碑完成時使用 [artifact-generation](./artifact-generation.md) 生成文檔
