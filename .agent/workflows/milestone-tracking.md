# 里程碑追蹤工作流程

此工作流程幫助Feature Owner有效地監控功能開發進度，識別風險，並確保按時交付。

## 里程碑管理原則

### 什麼是好的里程碑？

一個有效的里程碑應該：

- ✅ **可演示**：產出可以向利益相關者展示的成果
- ✅ **可測試**：有明確的驗收標準
- ✅ **有價值**：每個里程碑都增加業務價值
- ✅ **適當規模**：通常2-4週完成一個里程碑
- ✅ **依賴清晰**：里程碑間的依賴關係明確

### 典型里程碑結構

```
M0: 設計與規劃 (1週)
├─ 技術方案設計
├─ 架構審查
└─ 任務拆分完成

M1: 基礎設施 (2週)  
├─ 數據庫schema創建
├─ 基礎API框架
└─ 開發環境配置

M2: 核心功能 (3週)
├─ 主要業務邏輯實現
├─ 核心API完成
└─ 基本UI實現

M3: 完整功能 (2週)
├─ 所有功能完成
├─ 集成測試通過
└─ 文檔更新

M4: 優化與發布 (1週)
├─ 性能優化
├─ 全面測試
└─ 發布準備
```

## 工作流程步驟

### 步驟 1：里程碑初始化

創建里程碑追蹤文檔：

```bash
# 複製模板
cp templates/feature-owner/MILESTONE_TEMPLATE.md \
   docs/features/[feature-name]/MILESTONES.md
```

在文檔中定義每個里程碑：

```markdown
## M1: 核心功能實現

**目標日期**：2024-12-15
**負責人**：[姓名]
**狀態**：🟢 On Track / 🟡 At Risk / 🔴 Delayed

### 目標
實現核心業務邏輯和基礎API

### 包含的任務
- [x] TASK-001: 數據模型設計
- [/] TASK-002: 核心API實現  
- [ ] TASK-003: 業務邏輯層
- [ ] TASK-004: 單元測試

### 驗收標準
- [ ] 所有核心API端點實現並通過測試
- [ ] 單元測試覆蓋率 ≥ 80%
- [ ] API文檔完成
- [ ] 演示環境可用

### 風險與依賴
- ⚠️ 依賴外部API尚未就緒
- ⚠️ 部分技術棧團隊不熟悉

### 里程碑產物
- API文檔 v1.0
- 單元測試報告
- 技術決策記錄
```

### 步驟 2：設置追蹤節奏

建立定期檢查點：

#### 每日站會 (Daily Standup)
- **時間**：每天同一時間，15分鐘
- **參與者**：開發團隊
- **討論內容**：
  - 昨天完成了什麼
  - 今天計劃做什麼
  - 遇到什麼阻塞

#### 每週進度會 (Weekly Sync)
- **時間**：每週固定時間，30-45分鐘
- **參與者**：Feature Owner + 團隊 + 關鍵利益相關者
- **討論內容**：
  - 本週進展總結
  - 下週計劃
  - 風險和問題
  - 需要的支持

#### 里程碑審查會 (Milestone Review)
- **時間**：每個里程碑完成時
- **參與者**：完整團隊 + 利益相關者
- **討論內容**：
  - 里程碑成果演示
  - 驗收標準檢查
  - 經驗教訓
  - 下個里程碑規劃

### 步驟 3：更新任務狀態

每日更新任務狀態和進度：

#### 手動更新

編輯 `TASKS.md` 和 `MILESTONES.md`：

```markdown
- [x] 已完成的任務
- [/] 進行中的任務
- [ ] 待辦任務
- [!] 被阻塞的任務
```

#### 使用自動化工具

// turbo
```bash
# 更新里程碑狀態
python scripts/feature-owner/track_milestone.py \
  --feature "[feature-name]" \
  --milestone "M1" \
  --update
```

工具會：
- 掃描任務狀態
- 計算完成百分比
- 識別過期任務
- 生成進度報告

### 步驟 4：計算和監控關鍵指標

追蹤以下關鍵指標：

#### 進度指標

```markdown
### M1 進度概覽

**總體進度**：65% (13/20 任務完成)

**按優先級分類**：
- P0 (必須有): 80% (8/10)
- P1 (應該有): 50% (4/8)  
- P2 (可以有): 50% (1/2)

**按類型分類**：
- 後端: 70% (7/10)
- 前端: 60% (6/10)
- 測試: 0% (0/5)
- 文檔: 0% (0/2)
```

#### 速度指標 (Velocity)

```markdown
### 完成速度

**本週完成**：5 個任務
**上週完成**：6 個任務
**平均速度**：5.5 任務/週

**預測**：
- 剩餘任務：7 個
- 預計完成日期：12月18日
- 與目標日期差異：+3 天 ⚠️
```

#### 健康度指標

```markdown
### 項目健康度

**🟢 良好指標**：
- 測試覆蓋率：82%
- 代碼審查及時性：平均 4 小時
- 構建成功率：98%

**🔴 需要關注**：
- 3 個任務超期
- 2 個高優先級任務被阻塞
- 文檔更新滯後
```

### 步驟 5：識別和管理風險

主動識別和追蹤風險：

#### 風險識別檢查清單

每週評估以下風險類別：

**技術風險**
- [ ] 技術方案是否可行？
- [ ] 是否有技術債務累積？
- [ ] 性能是否符合預期？
- [ ] 安全性是否經過審查？

**進度風險**
- [ ] 是否有任務嚴重超期？
- [ ] 關鍵路徑上是否有阻塞？
- [ ] 速度是否符合預期？
- [ ] 範圍是否在持續膨脹？

**資源風險**
- [ ] 團隊成員是否過載？
- [ ] 是否有關鍵人員請假？
- [ ] 是否缺乏必要技能？
- [ ] 依賴團隊是否配合？

**範圍風險**
- [ ] 需求是否穩定？
- [ ] 是否有未預期的變更？
- [ ] 技術難度是否超出預估？

#### 風險記錄格式

```markdown
## 風險清單

### 🔴 高風險

**RISK-001: 外部API延遲交付**
- **影響**：阻塞M2的3個關鍵任務
- **概率**：高
- **影響程度**：高
- **緩解措施**：
  - 與外部團隊每日同步進度
  - 準備Mock API作為備選方案
  - 調整任務順序，優先非依賴任務
- **負責人**：張三
- **下次審查**：2024-12-10

### 🟡 中風險

**RISK-002: 新技術學習曲線**
- **影響**：可能延遲前端開發2-3天
- **概率**：中
- **影響程度**：中
- **緩解措施**：
  - 安排技術分享會
  - 結對編程
  - 準備技術文檔和示例
- **負責人**：李四
- **下次審查**：2024-12-12
```

### 步驟 6：生成狀態報告

定期生成里程碑狀態報告：

#### 每週狀態報告

```bash
# 生成週報
python scripts/feature-owner/track_milestone.py \
  --feature "[feature-name]" \
  --report-type "weekly" \
  --output "docs/features/[feature-name]/reports/week-[N].md"
```

週報內容：
- 本週完成的任務
- 下週計劃
- 當前進度 vs 目標
- 風險和阻塞
- 需要的支持

#### 里程碑完成報告

```bash
# 生成里程碑報告
python scripts/feature-owner/generate_artifact.py \
  --feature "[feature-name]" \
  --milestone "M1" \
  --type "milestone-report"
```

里程碑報告內容：
- 達成的目標
- 完成的任務清單
- 驗收標準檢查
- 關鍵指標總結
- 經驗教訓
- 下階段建議

### 步驟 7：里程碑驗收

每個里程碑完成時執行正式驗收：

#### 驗收檢查清單

```markdown
## M1 驗收檢查清單

### 功能完整性
- [ ] 所有計劃的任務都已完成
- [ ] 所有驗收標準都已滿足
- [ ] 功能可以成功演示

### 質量標準
- [ ] 單元測試覆蓋率達標 (≥ 80%)
- [ ] 集成測試通過
- [ ] 代碼審查完成
- [ ] 無高優先級缺陷

### 文檔完整性
- [ ] API文檔已更新
- [ ] 用戶文檔已更新（如適用）
- [ ] 技術決策記錄完成
- [ ] README更新

### 部署就緒
- [ ] 可以部署到測試環境
- [ ] 配置文檔完整
- [ ] 數據遷移腳本準備（如適用）

### 團隊準備
- [ ] 下個里程碑任務已規劃
- [ ] 團隊成員已分配
- [ ] 依賴已確認
```

#### 驗收會議

組織里程碑驗收會議：

**參與者**：
- Feature Owner
- 開發團隊
- 測試團隊
- 關鍵利益相關者

**議程**：
1. 功能演示（15分鐘）
2. 驗收標準檢查（10分鐘）
3. 質量指標審查（10分鐘）
4. 經驗教訓討論（15分鐘）
5. 下階段規劃（10分鐘）

### 步驟 8：調整和優化

根據實際進展調整計劃：

#### 何時需要調整？

**🟢 正常情況**：進度符合預期
- 繼續當前節奏
- 持續監控

**🟡 輕微偏差**：延遲1-3天
- 分析原因
- 調整下週計劃
- 增加每日同步頻率

**🔴 嚴重偏差**：延遲>3天或阻塞
- 召開緊急會議分析問題
- 考慮調整範圍或資源
- 更新利益相關者期望
- 制定補救計劃

#### 調整措施選項

**增加資源**
- 增加開發人員
- 外包部分任務
- 技術支持介入

**調整範圍**
- 將P2任務推遲到後續里程碑
- 簡化複雜功能
- 使用現有解決方案代替自研

**優化流程**
- 減少會議時間
- 並行執行更多任務
- 簡化審批流程

**延期交付**
- 誠實評估新時間線
- 與利益相關者溝通
- 調整後續里程碑

## 進度追蹤最佳實踐

### ✅ 應該做的

1. **保持透明**
   - 誠實報告進度和問題
   - 及早報告風險，不要隱瞞
   - 公開分享狀態報告

2. **數據驅動**
   - 用數據支持決策
   - 追蹤趨勢而非單點數據
   - 建立基準線以便比較

3. **主動溝通**
   - 定期更新利益相關者
   - 問題出現時立即通知
   - 慶祝小勝利

4. **持續改進**
   - 從每個里程碑學習
   - 調整估算方法
   - 優化流程

### ❌ 避免做的

1. **不要過度樂觀**
   - 誠實面對延遲
   - 不要承諾不確定的日期
   - 預留緩衝時間

2. **不要微觀管理**
   - 信任團隊成員
   - 關注結果而非過程
   - 給予自主權

3. **不要忽視警訊**
   - 重視團隊的擔憂
   - 不要等待問題惡化
   - 主動解決小問題

4. **不要孤軍奮戰**
   - 尋求幫助和支持
   - 與架構師和資深工程師協作
   - 利用團隊的集體智慧

## 檢查清單

里程碑追蹤運作良好的標誌：

- ✅ 每個人都清楚當前進度
- ✅ 風險被早期識別和處理
- ✅ 狀態報告定期更新
- ✅ 團隊有信心達成目標
- ✅ 利益相關者滿意溝通頻率
- ✅ 問題得到快速解決
- ✅ 數據驅動決策
- ✅ 持續改進流程
